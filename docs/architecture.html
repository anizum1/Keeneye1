Chain of custody · how it works

Inside KEENEYE

What actually happens between dropping a file on the page and it sitting sealed in the vault — and how the tool can later tell whether anything changed.

01 — Shape

Two front doors, one engine

The 3D interface and the command line are not two applications. Both call the same service layer, and nothing else is allowed to write. That is why an action taken in a terminal shows up in the ledger in the browser — there is only ever one log.

03 — Mechanism

Why an edited log gives itself away

Every entry's hash is computed over its own contents and the hash of the entry before it. Change a historical entry and its contents no longer hash to the value the log recorded — at a position the tool can name.

04 — Checking

Two questions, two different checks

These are easy to confuse and answer different things. Both write their outcome to the log — including when they fail, because a tool that records only its successes is worse than none.

Did the file change?

Re-hash the evidence

Reads the bytes back off disk — not the path, not a cached value — recomputes SHA-256 and compares it to the digest recorded at intake. Run per item, per case, or across everything.

coc verify --case 2026-100

Did the log change?

Walk the chain

Recomputes every entry's hash, checks each points at its predecessor, and checks the sequence has no gaps — which is what catches a deleted entry rather than an edited one. Reports the first broken position.

coc chain verify

05 — Storage

What is actually on your computer

Two things, in the workspace folder. They are one unit: the vault on its own is a pile of anonymous blobs, because the name, the case and the custody history all live in the database.

06 — Defences

Three layers, catching different attackers

Catches the app

Append-only triggers

The database aborts any UPDATE or DELETE against the custody log. This constrains the application — including a careless change made to it next year. It is not a security boundary: anyone with the file can drop a trigger in one line.

Catches file edits

Write-once vault

Content-addressed and read-only, so a modified file no longer matches the address it sits at. Re-hashing finds it.

Catches database edits

The hash chain

The one that survives someone bypassing the application entirely — the case the triggers cannot cover.

07 — Honestly

What it does not do

Stated with the same weight as the defences, because a forensic tool that oversells itself is worse than one that claims less.

  • Known gaps
  • A chain proves nothing was edited — not that nothing was removed from the end. Truncate the log and the surviving prefix stays perfectly consistent. The court report prints the chain head at the moment it was generated; a dated report that has left the building is what makes a later truncation visible.
  • Entries are chained but not signed. Anyone who can write to the database can append a valid new entry under any username. Per-examiner signing keys would fix it and are not implemented.
  • Timestamps come from the machine, not an authority. Source file times are claims the sending system made, and the log's own times come from the server clock. Proving when needs a trusted timestamp authority.
  • There is no write blocker, and it has never been validated. It hashes what it is given. If evidence was altered before it arrived, that altered version is recorded as authoritative. “The tests pass” is not “validated for casework”.
